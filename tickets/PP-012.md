## Acceptance criteria

1. The protected first-Admin setup command fails closed when an Admin already exists and reads the initial password through the approved hidden prompt. Login, session expiry, logout invalidation, cookie/CSRF handling, and generic credential errors follow SECURITY §§3-4 and the `/auth` API contract.
2. Backend authorization is enforced on every protected route using the current account status and role. Direct unauthenticated and Business User requests to Admin-only user operations are denied with the specified safe responses; client-side route guards do not substitute for backend checks.
3. Admin create/list/deactivate operations and `POST /admin/users/{user_id}/password-reset` follow API_SPEC. Temporary passwords are policy-compliant and write-only over TLS, normalized and hashed server-side with the approved Argon2id policy, never returned or logged. Reset sets `must_change_password`, atomically revokes every target session, returns only the public user representation, and requires the Admin to hand the temporary credential directly to the verified user in person outside ProductPulse. No recovery email or public self-service reset is added.
4. A user who signs in with a temporary password is marked `must_change_password` and cannot access normal application routes. The backend permits only session inspection, logout, and password change. The forced-change screen follows UI §4.1. A successful password change validates the current temporary password and new-password policy, stores the approved hash, clears the flag, revokes prior account sessions, and establishes one fresh session with rotated cookie and CSRF values.
5. Reset, password change, account creation/deactivation, sign-in/out, session revocation, and authorization-denial audit events follow SECURITY §12 and DATA_MODEL. Audit events include only approved safe fields; passwords, hashes, session/CSRF values, and other prohibited data are absent from audit snapshots, logs, responses, and errors.
6. PP-003 is approved and PP-010 is Done in M1. Dependencies remain PP-003 and PP-010. Detection, incident-producing results, and notifications remain fail-closed until their applicable approvals are recorded.
7. Each implementation criterion has mapped automated acceptance/security/API tests. Commands, results, revision identity, and evidence links are recorded before closure; any criterion requiring human observation also has a reproducible manual result.
